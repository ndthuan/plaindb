# Troubleshooting


`plaindb doctor` checks the store and its environment and prints every problem with the command that fixes it. It never changes the store. It exits 1 when any check is an error, and 0 when there are only warnings. `--json` prints the same result as `plaindb_doctor` returns to an agent; `--offline` leaves the remote alone.

- git: the binary and where it came from, whether the remote answers, commits not pushed, a remote that is ahead, the last push error, whether HEAD is on the configured branch, lock files a commit needs and their age (`index.lock`, `HEAD.lock`, `packed-refs.lock`, `config.lock` and any `*.lock` under `refs/`; one older than 10 minutes is an error), committed writes still waiting for their git commit, database files that differ from the last commit while no transaction waits for `plaindb commit`, commits made outside plaindb, and whether housekeeping keeps up with `gc_every`. Every command in a fix names the store path in single quotes, so it can be pasted into a shell as it is.
- store: journal records not yet checkpointed, the write lock held by another process, unreadable documents and schema failures with the first 10 ids, file names that differ only by letter case, files in a collection that are not read (`store_skipped_files`), attached files that are missing from disk (`attachment_missing`), that differ in size or SHA-256 from their document's `_files` (`attachment_mismatch`), or that lie under `_files` without a document that lists them (`attachment_orphan`), each with the first 10 as `<db>/<collection>/<id>/<name>`, an index cache out of step with the files, and the store format.
- environment: a network filesystem, filesystem case sensitivity, the durability level and what a power loss can lose at it, and free disk space below 1 GiB or 10%.

A missing git binary or an unreachable remote is an error when push is on and a warning otherwise. The attachment checks are warnings: a missing file is attached again with `plaindb file put` or forgotten with `plaindb file rm`, a changed file gets its right bytes back or is removed by hand before `plaindb file rm`, and an orphan file is removed by hand. The `journal` and `index_cache` warnings clear themselves, and can also show while another process is writing. `plaindb rescan` looks for edits made by hand, and `plaindb reindex` drops the index cache and reads every file again.
